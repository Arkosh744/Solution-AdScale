# Поток событий и Kafka

Statistics принимает события, Kafka доставляет их независимо от торгов, Finance учитывает деньги, Analytics строит отчеты.

## Устойчивый прием

1. Statistics проверяет источник и сохраняет событие с outbox в одной PostgreSQL-транзакции.
2. После COMMIT возвращается 202; фоновый обработчик публикует событие в Kafka.
3. Потребитель сохраняет результат и ключ обработки, затем подтверждает offset.

Доставка допускает повторы. Сбой после публикации до отметки outbox приводит к повторной отправке с прежним ID.

При недоступной Kafka журнал продолжает прием до установленного дискового предела. Если сохранить событие нельзя, возвращается 503; память процесса не заменяет устойчивую запись.

## Топики и потребители

| Топик | Ключ | Потребитель | Хранение |
|---|---|---|---|
| `ad.billing.v1` | reservation ID | `finance` | 7 суток |
| `ad.impressions.v1` | campaign ID | `analytics-impressions` | 7 суток |
| `ad.clicks.v1` | campaign ID | `analytics-clicks` | 7 суток |
| `campaign.updated.v1` | campaign ID | `bidding-cache` | Последняя версия, compaction |
| `ad.errors.v1` | event ID | Разбор ошибок | 30 суток |

В начальной конфигурации для каждого основного потока предусмотрено по 12 партиций. Число уточняется по пропускной способности и нужному параллелизму потребителей.

Kafka размещается в трех зонах: RF=3, `min.insync.replicas=2`, producer `acks=all` и идемпотентная публикация. Порядок гарантируется только внутри одной партиции; обработчики дополнительно проверяют версии и состояние операции.

## Формат

Выбран JSON с версией схемы: его удобно читать и использовать в гибридном стеке. Avro имеет смысл при измеренной проблеме объема или сериализации, но Schema Registry для первого этапа не требуется.

```json
{"schema_version":1,"event_id":"event-17","kind":"billable_impression","partner_id":"partner-1","advertiser_id":"advertiser-2","campaign_id":"campaign-3","reservation_id":"r-42-1","currency":"USD","amount_micros":1250,"occurred_at":"2026-11-18T10:00:00Z"}
```

`occurred_at` задает время события в UTC. Рекламодатель, валюта и сумма сверяются с резервом, а не принимаются как разрешение на списание.

Добавление необязательного поля совместимо. Изменение смысла или обязательных полей требует новой версии; сначала обновляются потребители.

## Повторы и ошибки

Finance использует reservation ID как ключ окончательной операции, общий для списания и освобождения. Новый event ID не разрешает второй финансовый эффект.

Необработанные финансовые события остаются в PostgreSQL до подтвержденного учета Finance, даже после семи суток Kafka. Ошибки и конфликты сохраняются для разбора с сигналом, а не пропускаются молча.

После переключения Kafka финансовые события без подтвержденной обработки публикуются заново из журнала с исходными ID. Старая отметка «опубликовано» не доказывает, что Finance завершил учет.

Analytics устраняет дубли по event ID до суммирования. Одно фоновое слияние ClickHouse или инкрементальная сумма поверх повторов этого не гарантируют.

Поздние события запускают пересчет затронутого дня по полному доступному источнику; отчет использует только завершенный результат пересчета. Если исходных данных уже нет, корректировка не объявляется успешной.

Сроки сырых данных и архива приведены в [стратегии хранения](database-strategy.md). Метрики потока: consumer lag, возраст outbox, число повторов, ошибки и заполнение диска.
