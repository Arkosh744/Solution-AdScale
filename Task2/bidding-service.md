# Сервис ставок Bidding

Bidding на Go принимает запрос, подбирает кампанию, рассчитывает аукцион и возвращает ставку. Данные кампаний заранее загружены в память; финансовые резервы хранятся в собственной PostgreSQL.

Сервис не строит отчеты, не обрабатывает платежи и не читает таблицы монолита. Существующий алгоритм C++ используется через локальный адаптер.

## Внешний API

Выбран профиль OpenRTB 2.6: HTTPS/JSON, баннеры, USD и цена CPM. Партнер отправляет запрос в AdScale. `imp` обозначает рекламное место; в одном запросе допускается до десяти мест и до 64 КиБ данных.

| Маршрут | Назначение | Результат |
|---|---|---|
| `POST /openrtb2/auction` | Рассчитать ставку | 200 со ставкой, 204 без ставки |
| `POST /v1/partners/{partner_id}/events` | Принять уведомление через Statistics | 202 после устойчивого сохранения |
| `/readyz`, `/livez` | Проверить готовность и состояние | Только внутренняя сеть |

Некорректный запрос дает 400, отказ доступа - 401/403, конфликт request ID - 409, превышение квоты - 429, техническая недоступность - 503. Ответ 204 имеет пустое тело.

Пример запроса:

```json
{"id":"req-42","imp":[{"id":"imp-1","banner":{"w":300,"h":250},"bidfloor":1.0,"bidfloorcur":"USD"}],"site":{"id":"site-7"},"tmax":80,"cur":["USD"],"at":1}
```

Пример ответа; `reservation_id` в расширении связывает ставку с финансовым уведомлением:

```json
{"id":"req-42","seatbid":[{"seat":"adscale","bid":[{"id":"bid-42-1","impid":"imp-1","price":1.25,"adm":"<img src=\"https://cdn.example/banner-7.png\">","crid":"creative-7","ext":{"reservation_id":"r-42-1"}}]}],"cur":"USD"}
```

Цена 1,25 USD CPM означает 0,00125 USD за показ. Денежные суммы рассчитываются целыми микроденежными единицами, не через `float64`. Адрес `.example` иллюстрирует формат, а не работающий сервис.

## Обработка запроса

1. Проверить партнера, формат и оставшееся время общего дедлайна.
2. При повторе найти сохраненный результат по `(partner_id, request_id)`.
3. Выбрать кампании из актуальной локальной копии и рассчитать ставку без денежных изменений.
4. Одной транзакцией проверить выделенный лимит, создать резервы выбранных мест и сохранить весь ответ. Обычный no-bid также сохраняется.
5. Вернуть ответ только после подтвержденного COMMIT и до срока доставки партнеру.

Уникальный ключ запроса не дает двум конкурентным обработчикам создать два набора резервов. Повтор чистого расчета допустим, повтор денежного эффекта - нет.

Идентичный повтор получает сохраненный результат; другое содержимое с тем же ID дает 409. После исходного срока ставка повторно не отправляется: возвращается 204 без перезаписи результата.

При неизвестном COMMIT возвращается технический отказ. Результат затем проверяется по тому же ключу; новый независимый резерв не создается. Уже записанный резерв сохраняется даже при потере ответа партнером.

## Основные данные

| Объект | Ключевые данные |
|---|---|
| CampaignSnapshot | Кампания, рекламодатель, валюта, версия, статус, таргетинг, срок актуальности |
| BudgetLimit | ID выделения, рекламодатель, валюта, пул Bidding, сумма и доступный остаток |
| RequestResult | Партнер и request ID, отпечаток запроса, исходный срок, сохраненный ответ |
| Reservation | ID, request/imp ID, кампания, выделенный лимит, максимальная сумма, состояние |
| Outbox | ID операции, содержимое, состояние отправки |

Окно повторов составляет 24 часа; партнер не переиспользует ID в этом окне. Ключи хранятся не меньше этого срока. Незакрытые резервы и связанные финансовые записи не удаляются по его истечении.

## Бюджет и списание

Finance остается единственным владельцем общего баланса. Он заранее выделяет ограниченные суммы пулам Bidding; сумма выданных лимитов и уже учтенного расхода не превышает бюджет рекламодателя.

Внутри пула несколько экземпляров Bidding используют один транзакционный учет. Проверка принадлежности кампании рекламодателю и валюте, уменьшение доступного остатка и создание резервов выполняются атомарно. Перезапуск не восстанавливает израсходованный остаток.

Подтвержденный показ передается через Statistics и Kafka в Finance. Уведомление о победе само по себе не является основанием списания.

1. Finance проверяет принадлежность резерва партнеру и сумму уведомления.
2. Идемпотентная команда Bidding закрывает резерв как списанный либо освобожденный. Эти исходы взаимоисключены; сумма не превышает резерв.
3. Finance фиксирует расход и отметку обработки в одной транзакции, используя reservation ID как ключ окончательной операции.

Повтор с тем же исходом и суммой возвращает прежний результат; другой исход, сумма или валюта дают конфликт и сверку. Пока расход не принят Finance, соответствующая сумма остается занятой. Остаток после частичного окончательного списания возвращается в доступный лимит пула.

Освобождение требует подтвержденного отсутствия обязательства по правилам партнера или сверки. Потерянный ответ, отсутствие события и тайм-аут не освобождают деньги автоматически.

Лимиты старого и нового путей не пересекаются. Перенос неиспользованной суммы допускается после остановки ее использования и сверки; поздние уведомления продолжают закрывать исходные резервы.
