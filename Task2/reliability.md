# Надежность и деградация

## Основные паттерны

- Circuit Breaker временно прекращает обращения к постоянно ошибающейся зависимости
- ограниченные пулы и очереди изолируют перегрузку одного направления
- фоновые операции повторяются с экспоненциальной задержкой и случайным разбросом
- финансовые повторы сохраняют исходный идентификатор операции

Начальная политика фоновых повторов: 100 мс с удвоением до 5 с. После серии неудач операция остается в устойчивом журнале и подает сигнал; она не удаляется из-за исчерпания числа попыток.

В RTB повторов сетевых вызовов и транзакции нет. После неизвестного COMMIT используется [сохраненный результат Bidding](bidding-service.md), а не новая денежная операция.

## Поведение при отказах

| Ситуация | Поведение |
|---|---|
| Redis недоступен | Работать с еще актуальной локальной копией; после ее срока прекратить положительные ставки |
| Campaign недоступен | Не продлевать актуальность старых данных |
| Finance недоступен | Использовать ранее выделенные лимиты; после исчерпания прекратить ставки |
| PostgreSQL Bidding недоступна | 503, без положительной ставки из кеша |
| Неизвестен результат COMMIT | Технический отказ и проверка по прежнему request ID |
| Kafka недоступна | Сохранять события в журнале Statistics и доставлять позже; при заполнении журнала возвращать 503 |
| Analytics недоступен | Торги продолжаются, отчеты запаздывают |
| Расчет завершился поздно | Не отправлять ставку после дедлайна; созданные резервы сохранять |

Параллелизм C++-вызовов ограничен. Зависший native-вызов не отменяется одним Go context: экземпляр снимается с приема и заменяется, а состояние восстанавливается из БД.

## Резервная стратегия

Кешированная цена допустима как вход расчета при актуальной кампании и новом подтвержденном резерве. Чужой сохраненный bid-response не подходит другому запросу.

При неизвестном бюджете дефолтная положительная ставка запрещена. Безопаснее отказ от участия; отказ зависимости учитывается как техническая ошибка, а не успешный экономический no-bid.

## Финансовые повторы

Уникальный reservation ID, проверка состояния резерва и транзакционная отметка обработки исключают повторное списание. Списание и освобождение одного резерва взаимоисключены.

Поздние уведомления обрабатываются после отката маршрута. Перед повтором платежа с неизвестным исходом Finance проверяет статус у платежного провайдера; новый ключ списания не создается.

## Проверка доступности

Для годовой цели SLA 99,9% предложено месячное окно. Считать долю вовремя и корректно обработанных запросов; ошибки зависимостей и массовые технические отказы не скрываются быстрым 204.

Проверить повтор уведомления, сбой после COMMIT, отказ Redis/Kafka, переполнение журнала и переключение региона.
