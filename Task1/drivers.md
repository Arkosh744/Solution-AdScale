# Архитектурные драйверы

Решение должно подключить нового партнера без полной переработки монолита и сохранить возможность дальнейшего роста.

## Функциональные требования

- прием запросов на ставки, подбор рекламы, расчет аукциона и возврат ответа
- управление кампаниями, ставками и бюджетами
- выдача рекламных материалов
- прием показов и кликов, потоковая обработка через Kafka
- однократное списание подтвержденного расхода, учет платежей и балансов
- отчеты без тяжелых запросов в БД торгов
- подключение нескольких рекламных платформ через отдельные адаптеры

## Требования к качеству

| Приоритет | Требование | Критерий |
|---|---|---|
| Высокий | Производительность через три месяца | Не менее 18 000 RPS, общий P95 не выше 100 мс |
| Высокий | Интеграция с новым партнером | Полный ответ не дольше 80 мс с учетом меньшего `tmax` |
| Высокий | Финансовая корректность | Повтор уведомления не создает повторного списания |
| Высокий | Непрерывность | Постепенное переключение без остановки всех клиентов |
| Средний | Масштабирование через год | 50 000 RPS, горизонтальное добавление экземпляров |
| Средний | Доступность через год | Несколько регионов, SLA 99,9% |
| Средний | Восстановление | RPO/RTO, резервные копии и проверка восстановления |
| Средний | Эксплуатация | Контейнеры, автоматическое развертывание, метрики и трассировки |

80 мс относится к новому партнеру, а P95 100 мс - ко всей платформе. При проверке старые маршруты оцениваются отдельно: быстрые отказы новому партнеру не должны скрывать их деградацию.

## Ограничения

- срок первого этапа - три месяца, бюджет ограничен
- полная перепись системы запрещена
- в компании 35 сотрудников разных специальностей, выделенного SRE нет
- начальная система - гибридный монолит, одна PostgreSQL, один кластер
- годовое решение должно быть микросервисным и событийным

Для хранилищ и контейнерной платформы выбраны управляемые сервисы, чтобы сократить объем ручного сопровождения.

## Основные правила

1. Убрать тяжелую аналитику и обработку событий из критического пути торгов.
2. Подготавливать данные кампаний заранее; не читать общую БД при каждом новом аукционе.
3. Не считать кешированный бюджет разрешением на расход: лимиты и резервы проверяются транзакционно.
4. Назначить одного владельца записи каждому набору данных.
5. Не освобождать неизвестное финансовое обязательство только по тайм-ауту.

Партнер отправляет OpenRTB-запрос в AdScale. Finance списывает средства только после подтверждения показа; уведомление о победе само по себе не запускает списание.

TTL, RPO/RTO и бюджеты времени выбраны при проектировании; их допустимость проверяется перед внедрением. Решение и этапы перехода описаны в [TO-BE](TO-BE.md).
