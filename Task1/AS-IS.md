# AS-IS: диагностика AdScale

AdScale обрабатывает 15 000 запросов на ставки в секунду с P95 110-120 мс при требовании 100 мс. Подключение партнера увеличивает пик до 18 000 RPS и вводит отдельный предел ответа 80 мс.

Основная проблема - общая PostgreSQL: аукцион читает ее синхронно, статистика постоянно пишет события, аналитика выполняет тяжелые запросы. Добавление экземпляров монолита не устраняет этот общий ограничитель.

## Текущие компоненты

| Компонент | Назначение | Проблема |
|---|---|---|
| Ad Server | Прием запросов, подбор рекламы | Чтение общей БД |
| Auction Engine | Правила торгов, выбор победителя | Синхронные обращения в БД |
| Delivery | Подготовка HTML/JS и ответа | Зависимость от результата аукциона |
| Statistics | Запись показов и кликов | Нет буферизации |
| Finance | Балансы, списания, счета | Общая БД с остальными функциями |
| Analytics | Отчеты | Тяжелые запросы в основной БД |
| Dashboard | Управление рекламой | Общие данные и развертывание |

Это части одного гибридного монолита на C++, Go, Python и Node.js, а не независимо развертываемые микросервисы. В системе нет кеша, очередей, контейнеризации и автоматического развертывания.

## Узкие места

| Приоритет | Наблюдение | Последствие |
|---|---|---|
| Высокий | Единственный экземпляр PostgreSQL | Отказ БД останавливает зависимые функции |
| Высокий | SQL аукциона конкурирует со статистикой и аналитикой | Задержки БД увеличивают время торгов |
| Высокий | P95 уже превышает 100 мс | Для нового партнера недостаточно добавить только 20% мощности |
| Средний | Нет очереди событий | Всплески записи сразу нагружают PostgreSQL |
| Средний | Монолит развертывается целиком | Нельзя независимо масштабировать и выпускать нагруженную часть |
| Средний | Один кластер и ручное развертывание | Длительное восстановление и риск ошибок при изменениях |

Синхронное чтение Auction Engine задано явно. Ожидает ли ответ на ставку записи статистики, из условия неясно. Конкуренция за ресурсы БД существует в обоих случаях.

Обычный `SELECT` в PostgreSQL не блокирует все записи. Причины блокировок нужно проверять по реальным запросам и транзакциям.

## Что измерить перед внедрением

- задержки подбора, расчета, SQL и формирования ответа по трассировкам
- CPU, дисковый ввод-вывод, соединения и медленные запросы PostgreSQL
- число, размер и пиковую частоту событий
- ошибки, опоздавшие ответы и долю no-bid отдельно по партнерам

Рабочая гипотеза связывает рост задержек с конкуренцией за БД. Если измерения покажут ограничение в вычислениях, первым шагом становится оптимизация и масштабирование аукциона.
